### Slide 2 — The Engineering Philosophy (Independent Reconstruction)
**Speaker Notes (≈220 words)**:
Our engineering philosophy has five pillars, and they're not aspirational — they're enforced by review. First, independent reconstruction: we reimplement from specifications, not port code. This catches assumptions the original author didn't document. The Box TypeScript port (models/the-box.ts) was written from THE_BOX_MASTER_DOCUMENTATION.md, not from reading kernel.py. Second, real calculations: no mocks in tests. If a test says "compute lineage depth," it computes lineage depth on real graph data, not a stub. Third, determinism: every experiment uses fixed seeds (42–71 for ORACLE, 1–3 for The Box R1). SplitMix64 RNG in showcase, Python's random with explicit seeds in The Box. Fourth, intermediate stages exposed: debug panels show per-step state, not just final output. The showcase demos have "Show Intermediate" toggles. Fifth, honest fidelity classification: Level 1 = spec only, Level 2 = structural skeleton, Level 3 = structural properties match (The Box TS), Level 4 = byte-for-byte where applicable (Showcase demos). The Box TS is Level 3 — node counts, degree distributions, Betti numbers match Python; only BLAKE2b hashes differ because our pure-TS BLAKE2b isn't byte-compatible with hashlib.blake2b. This philosophy scales: 182 tests across 5 demos, 160 kB bundle, zero runtime dependencies.

### Slide 4 — The Box: Relational Substrate — One-Slide Summary
**Speaker Notes (≈240 words)**:
The Box is an arc-incidence multi-digraph. The critical architectural decision: nodes and arcs share ONE identifier space (CL-0001). An arc is (src: Id, dst: Id, tag: Tag). Because IDs are shared, arcs can target other arcs — this gives you hypergraph expressivity with simpler implementation. The kernel maintains four incidence maps: node→outgoing, node→incoming, arc→outgoing, arc→incoming. All operations O(1) via dict. The kernel knows NOTHING about identity, lineage, or generation (CL-0003) — those are derived post-hoc from arc tags in identity.py. Six rewriting rules operate as DATA in YAML (foundry.yaml), not hardcoded (CL-0002): GATHER collects compatible nodes, BOND forms pairwise links, TAG_PROP propagates tags along arcs, QUIET suppresses high-activity nodes, DESCEND creates meta-arcs from arcs (arc→arc), FUSE merges equivalent structures. Rule engine: predicates bind pools, effects apply atomically per step. Scheduler: sequential (fixed order) or random (shuffled per step). 557 Python tests pass (CL-0008), 102 TypeScript tests pass (CL-0008). Two core defects block generality (CL-0006): since_inflow semantics bug (starvation miscounted by 10×), and Rule.to_dict() omission (FUSE fires 4× not 5×). These are in SOURCE_INVENTORY.md §5. One admitted phenomenon: mean_depth survives gates G0–G4 at p=0.00111, explained by DESCEND mechanism (CL-0004).

## ACT 2: THE BOX DEEP DIVE

### Slide 10 — Kernel Architecture: Arc-Incidence Multi-Digraph
**Speaker Notes (≈250 words)**:
The kernel is the heart of The Box. State = (nodes: Set[Id], arcs: Map[Id, Arc], id_counter: int). Arc = (src: Id, dst: Id, tag: Tag). The critical invariant (CL-0001): nodes and arcs share ONE identifier space. This means an arc's ID can appear as src or dst of another arc — arcs can target arcs. This gives hypergraph-like expressivity (edges as nodes) without hypergraph complexity. The kernel maintains four incidence maps for O(1) traversal: node_outgoing: Map[Id, Set[Id]], node_incoming: Map[Id, Set[Id]], arc_outgoing: Map[Id, Set[Id]], arc_incoming: Map[Id, Set[Id]]. When you add an arc, you update all four maps. When you delete, you clean all four. No adjacency lists — incidence is the primary structure. The kernel (src/thebox/kernel.py lines 10-37) has ZERO knowledge of identity, lineage, generation (CL-0003). Those are derived in identity.py from arc tags post-hoc. This separation is deliberate: the kernel is a pure relational substrate; meaning is layered on top. Memory overhead: ~4× dict entries vs adjacency list, but enables arc-as-endpoint queries in O(1). Serialization: JSON export dumps nodes, arcs, id_counter. Import reconstructs incidence maps. Scale: tested to ~10k nodes, ~30k arcs in 900 steps. The 557 tests exercise every kernel mutation path. The TypeScript port (models/the-box.ts) replicates this architecture exactly — same incidence maps, same O(1) guarantees.

### Slide 11 — The Six Rules as Data: YAML DSL
**Speaker Notes (≈260 words)**:
The six rules are NOT hardcoded in Python. They're data in foundry.yaml, parsed by a rule DSL in rules.py (CL-0002). The DSL has: predicates (filter candidates), channels (group by tag), selectors (choose from pools), pools (bound variable sets), effects (mutate graph). A rule: name, predicates[], channels[], selectors[], pools[], effects[]. Effect types: create_arc(src_pool, dst_pool, tag), tag(target_pool, tag), untag(target_pool, tag), delete(target_pool). Rule engine: for each step, for each rule in scheduler order: evaluate predicates → bind pools via selectors/channels → apply effects atomically (all or nothing). Scheduler: sequential (fixed order: GATHER, BOND, TAG_PROP, QUIET, DESCEND, FUSE) or random (shuffle per step). GATHER: finds compatible node pairs (predicate: same tag, not connected) → creates arcs (BOND-ready). BOND: forms pairwise links from GATHER pairs. TAG_PROP: propagates tags along arc paths (transitive closure-ish). QUIET: suppresses nodes with degree > threshold (prevents runaway hubs). DESCEND: creates meta-arcs — new arc whose src/dst are existing arcs (arc→arc). This is the engine of open-endedness. FUSE: merges structurally equivalent subgraphs (isomorphism-ish). The YAML format means you can version rule sets, compose new rule sets, ablate rules for experiments (R5 removes DESCEND). The TypeScript port parses the SAME foundry.yaml — cross-language rule parity validated in the-box-validation.test.ts.

### Slide 12 — Identity & Lineage: Derived, Not Stored
**Speaker Notes (≈240 words)**:
Identity is not in the kernel (CL-0003). identity.py computes everything from arc tags post-hoc. Descent: arc α descends from β if β.tag ∈ α.tag_ancestry (tags accumulate via TAG_PROP and DESCEND). Lineage depth = longest descent chain from a ROOT (no ancestors). Identity classes: ROOT (no ancestors), DERIVED (has ancestors), FUSED (multiple ancestors via FUSE). Generation = lineage depth. This derivation is O(n²) per snapshot — we compute all-pairs descent. Why not store incrementally? Because null models require SHUFFLING tags and recomputing. If identity were stored, null models would need to rewrite kernel state. By deriving, null models are: permute tags → recompute identity → compare statistic. This enables: G0 (shuffle all tags), G1 (degree-preserving shuffle), G2 (component-preserving), G3 (tag-distribution-preserving), G4 (max of G0–G3). Ablation studies: remove DESCEND → recompute identity → lineage depth collapses (R5). Counterfactuals: rewrite tag history → recompute. Cost: 900-step run, ~10k arcs → ~100M descent checks per snapshot. We cache per-snapshot. The TypeScript port replicates identity.py exactly — same derivation, same null model pipeline. This is why cross-language validation works for structural properties (lineage depth distributions match) but not hashes (BLAKE2b differs).

### Slide 13 — Experiment Inventory R1: The Admitted Phenomenon (mean_depth)
**Speaker Notes (≈250 words)**:
R1 is the only preregistered statistical experiment in The Box. Standard ruleset, 900 steps, 3 seeds (1,2,3), 900 surrogates per null model (G0–G4). Statistic: mean lineage depth across all arcs at final step. Result: p=0.00111 at G4 (the maximum null). Invariance across window sizes: 0.000 / 0.059 / 0.088 (CL-0004). Status: ADMITTED (EXPLAINED) — the mechanism is DESCEND, which creates meta-arcs that increase lineage depth. This is NOT a discovery — it's an explanation. We knew DESCEND creates arc→arc links; we hypothesized this would increase mean_depth; we confirmed it. The "admitted" label means: phenomenon real, mechanism explained, but not *discovered* by the experiment. The experiment was confirmatory, not exploratory. Why only 3 seeds? Computational cost: 900 steps × 900 surrogates × 5 nulls × 3 seeds = 12.15M graph derivations. Each derivation O(n²). Took ~18 minutes on 2023 hardware. The 900 surrogates per null give stable p-values. Invariance: we window the trajectory (early/mid/late) and check if p-value stability holds. 0.000 / 0.059 / 0.088 means early window is perfectly invariant, mid/late have some drift but well below significance threshold. This is the ONLY statistic surviving all gates. No other statistic (node count, arc count, degree moments, beta0, beta1, clustering) survives G4. We've looked.

### Slide 14 — Experiment Inventory R5: DESCEND Structural Finding
**Speaker Notes (≈260 words)**:
R5 is a structural ablation — not statistical, deterministic given seed. 164 conditions: 8 initial structures × 2 schedulers (sequential/random) × ~10 seeds each, 300–600 steps. Condition: DESCEND present vs DESCEND absent (rule removed from foundry.yaml). Result: DESCEND absent → ALWAYS reaches FIXED_POINT (graph stops changing, no rule fires). DESCEND present → NEVER reliably settles (ongoing meta-arc creation) (CL-0005). 100% concordant across 164 runs. Mechanism: DESCEND creates arcs whose endpoints are arcs (arc→arc). These meta-arcs can themselves become endpoints for future DESCEND firings → infinite regress potential. QUIET and FUSE *can* intervene (QUIET suppresses high-degree nodes, FUSE merges equivalent structures), but they don't reliably catch the regress. The "structural finding" label means: this holds for all tested structures and schedulers, deterministically. It's not a p-value — it's a logical consequence of the rule semantics. We tested 8 structures: empty, single node, chain, star, cycle, complete, random sparse, random dense. Both schedulers. The finding suggests DESCEND is the engine of open-endedness — without it, the system always converges to a fixed point; with it, the system generates unbounded meta-arc structure unless suppressed. This is why mean_depth survives null models: DESCEND systematically increases lineage depth. The TypeScript port reproduces this exactly — same 164 conditions, same 100% concordance.

### Slide 15 — Experiment Inventory R6 & R6-Confirm: Mechanism Validation
**Speaker Notes (≈270 words)**:

Metric: "mechanism flip direction" — does the intervention reverse the DESCEND-driven lineage depth increase? Result: intervention flips 7/12, control flips 0/12, sign test p=0.00098 (EXP-BOX-R6). ### Slide 16 — Two Core Defects Blocking Generality
**Speaker Notes (≈280 words)**:
Two defects in the Python kernel block generality (CL-0006, SOURCE_INVENTORY.md §5). Defect 1: `since_inflow` semantics bug. The QUIET rule uses `since_inflow` to measure steps since a node last received an arc. Bug: counter increments on ALL steps, not just inflow steps. Result: node that received arc 5 steps ago reports 50 steps starvation (10× overcount). This causes QUIET to suppress nodes prematurely, breaking the intended dynamics. Defect 2: `Rule.to_dict()` omission. The FUSE rule is missing from the rule serialization dictionary. When experiment runner serializes rules for reproducibility, FUSE is omitted. Result: FUSE fires 4× instead of 5× over 300 steps; final graph hashes differ between runs with/without serialization. This breaks experiment reproducibility — the same seed gives different results depending on whether you serialized. Both defects were found by the test suite's cross-run hash comparison (557 tests include hash consistency checks). The since_inflow bug survived because tests used synthetic graphs with controlled inflow timing. The Rule.to_dict() omission survived because FUSE fires rarely in short tests. Impact: non-determinism across ports (TS port doesn't have these bugs — it reimplemented correctly), FUSE under-firing breaks fusion semantics, starvation gates misfire. Fix requires: kernel counter redesign (separate step counter vs inflow counter) + rule serialization overhaul (automatic registry, not manual dict). Priority: high — these block Level 4 fidelity and distributed runs. The TypeScript port (models/the-box.ts) does NOT have these defects — independent reconstruction caught them.

### Slide 22 — Coordination: Reputation-Weighted Voting + Bandit Adaptation
**Speaker Notes (≈250 words)**:
Coordination mechanism: reputation-weighted voting + bandit adaptation (CL-0012 key algorithm). Reputation: exponential moving average of verified solution quality. Formula: rep_t = (1-α)×rep_{t-1} + α×verified_quality, α=0.1. Verified_quality comes from verification engine — NOT agent self-report. New agents start at reputation=1.0 (neutral). Coordinator: collects proposals from all agents → weights by reputation → weighted random selection (or argmax). Bandit adaptation: each agent has policy arms (GreedyOptimizer: [greedy, random]; ConservativeOptimizer: [conservative, random]; AdaptiveStrategist: [ucb1, greedy, conservative, random]). UCB1 formula: score = mean_reward + sqrt(2*ln(total_pulls)/arm_pulls). Reward = verified improvement over previous best. Exploration bonus ensures all arms tried. Communication: Communicator broadcasts top-3 solutions every N steps. SkepticEvaluator receives all proposals, verifies locally, emits CHALLENGE if discrepancy > 5%. Other agents observe broadcasts, update local candidate pools. No synchronous rounds — async message passing via Redis (in ORACLE) or in-process queue (in SINGULARITY). Cold-start: new agents get neutral reputation, explore via bandit. Reputation collapse prevention: minimum weight floor (0.05), reputation decay for inactivity. The system is designed so that no single agent can dominate indefinitely — if one agent's proposals stop improving, its reputation decays, others get weight. This is testable: we can simulate reputation dynamics in isolation.

### Slide 23 — Verification Engine: Never Trusts Self-Reports
**Speaker Notes (≈240 words)**:
The verification engine is the epistemic backbone (CL-0010, oracle-singularity/backend/app/verification/verifier.py). Principle: NEVER trust agent self-reports. Every agent proposal is recomputed from ground truth. For E1 (Rastrigin): agent proposes x ∈ ℝ¹⁰, reports f(x). Verifier receives x, computes f(x) directly using the same Rastrigin implementation, compares. If |reported - verified| > 1e-9 → discrepancy_flag. For E2 (Resource Allocation): agent proposes allocation vector, verifier simulates environment, computes actual return. Verifier runs in separate process (Python subprocess) with same seeds — deterministic, isolated. Reports: verified_quality, agent_reported_quality, discrepancy_flag, latency_ms. This enables: (1) honest comparison — we know exactly what each agent *actually* achieved vs claimed. (2) Reputation based on verified quality, not reported. (3) Detection of bugs, cheating, numerical instability. (4) Negative result credibility — we verified the collaborative underperformance isn't a reporting artifact. Latency budget: <50ms per verification (Rastrigin eval is cheap). For expensive environments, we'd cache or approximate — but current environments are cheap. The verifier is the ONLY component that knows the ground truth function. Agents see only their local observations. This separation is why we can say "collaborative underperforms" with confidence — it's verified, not reported.

### Slide 26 — Statistical Rigor: Paired, Holm-Bonferroni, Bootstrap, Power
**Speaker Notes (≈240 words)**:
Methodology (CL-0011, oracle-singularity/docs/METHODOLOGY.md). Paired comparisons: same 30 seeds across all 4 conditions → 30×4 matrix. Pairwise differences computed per seed → 30 differences per pair. 6 pairs (4 choose 2). Test selection: Shapiro-Wilk normality on differences → if normal, Welch's t-test (unequal variance); if not, Wilcoxon signed-rank. Multiple comparison correction: Holm-Bonferroni (step-down, controls FWER). Why not Benjamini-Hochberg? We control family-wise error rate, not false discovery rate — we want NO false positives among the 6 pairs. Bootstrap 95% CI: 10,000 resamples of the 30 differences → percentile CI. Cohen's d: mean_difference / pooled_sd. Power analysis: 30 trials → 80% power to detect d=0.5 at α=0.05 (two-tailed). All reported in generated HTML reports (oracle-singularity/data/reports/*.html). Preregistered analysis: the statistical pipeline is fixed before data collection. No p-hacking: we don't peek, we don't swap tests post-hoc. The verification engine ensures the data is clean before statistics. This rigor is why we can say "VERIFIED negative result" — the negative survived the same gauntlet a positive would. For E2 (Resource Allocation), same pipeline, but only 1 environment run so far → EXPERIMENTAL tier. When we run E2 across multiple environments/seeds, it can become VERIFIED.
